# Pedagogy · 补齐理解的台阶

在写草稿时读取；章节顺序由 [knowledge-chain.md](knowledge-chain.md) 决定，数学和实现细节由 [technical-depth.md](technical-depth.md) 负责。

## What / Why before How

核心概念出场前先让读者知道任务和困难：我们要做什么？朴素方法已经做到什么？在哪个具体条件下不够用？新概念打算改哪一步？再给名称、定义、公式和实现。

例如讲索引，先给“为一个精确条件扫描大量不匹配记录”的工作量，再讲如何缩小候选范围。不要先列一串树的名字。如果读者已懂前置方法，只回顾本节需要的结论。

## 大白话与技术精度

正文用连贯段落解释因果，术语首次出现就交代作用。专业词负责精确，大白话负责让人跟得上；语言简洁不等于省略机制。

将抽象结论落实到可追踪的变化：

| 抽象说法 | 必须补出的台阶 |
| --- | --- |
| 降低方差 | 哪个随机量、哪种采样、减去／平均了什么、期望是否改变、需要哪些条件 |
| 提高稳定性 | 哪个量的变化被控制、用什么操作、控制范围到哪里，是否只是经验改善 |
| 增强表达能力 | 原先表示不了什么，新增参数／结构如何表示，代价是什么 |
| 提升效率 | 减少哪段计算或 IO，时间／空间／通信代价如何转移，何时不划算 |

语言中的力度必须受公式和证据约束。“减小一种风险”不写成“保证稳定”，“仍有梯度”不写成“强力纠正”。

## 初学者断点检查

沿一次真实推导或执行过程，从适用于当前主题的问题中找第一次可能掉队的位置；概率、梯度与训练相关项仅用于涉及它们的主题：

- 输入／变量从哪里来，之前是否产生过？
- 为什么能替换、交换、约掉或忽略这一项，前提是否满足？
- 这句话是定义、定理、估计还是近似？
- 理论上的期望用什么数据估计，实际算的是什么？
- 谁参与梯度，谁应固定，为什么需要 detach？
- 同名量在两个阶段是否变化，相似公式是否在优化不同对象？
- 训练与推理、离线准备与在线查询分别执行哪些步骤？

在断点处用短段落、最小例子或关键推导补台阶。只补后续理解实际依赖的前置内容；高成本旁支给作用和学习入口即可。

## Concrete example before abstraction

陌生抽象关系优先从一个能看出差异的具体问题进入，再归纳一般规律。例子应揭示行为变化或边界，不只是代入数字。能用符号与方向讲清的内容，不强塞算术；读者已有直觉时可以直接精确化。

例如容量为 2 的缓存，访问 A、B、A 后再放 C，可以暴露“最近插入”与“最近使用”的差别；此时再定义淘汰策略，概念就有了落点。

## Mechanism-aligned analogy

比喻只在能帮助判断行为时使用。角色对应技术对象，动作对应公式或操作，并能在条件变化后预测结果。

推荐展开：**条件 → 实际选择／操作 → 结果 → 一句人话。**

例如“最近使用的一端”像一个队尾：访问命中 → 移到队尾 → 满时移除另一端 → “用过就往后排”。这里位置表示访问次序，不表示重要性，也不能推出它总能留下未来最有用的数据。

先有机制解释，再用一句比喻唤回。比喻不是证明，不把类比说成等价；机制已经清楚时无需另编故事。

## 展开 → 归纳 → 一句话记忆

对分段函数、采样选择、缓存策略等，先列齐决定行为的重要条件，包含相等点、零值或无效输入等相关边界。说明各分支实际发生什么，再按共同机制归并为少量模式，最后压缩成一句准确的话。

总结必须保留关键条件。不能从一个分支的结果推出整个系统都停止更新，也不能给读者一条脱离条件的口诀。

## 节奏与真实性

列表用于并列项，表格用于共同维度比较、条件分支与符号映射；因果解释留在段落中。提示卡只标出有功能的转折、洞察或误解，不把每段都装进盒子。

讲解顺序不等于历史顺序。不同路线、互补机制与替代方案明确分开；不存在的缺口不硬编，不用“后来发明了”制造未经来源支持的继承关系。

重要章节结尾压缩核心结论，并给具体停止标准，例如“能在容量为 2 的访问序列上手推淘汰结果，解释为何命中也要改变顺序”。不要求每节都有比喻、表格、代码或面试题。
