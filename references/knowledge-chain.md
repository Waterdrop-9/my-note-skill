# Knowledge Chain · 让下一块知识有来处

在写正文之前读取。知识链是依赖与问题关系，可以有分支，不是名词目录或固定历史进化链。

## 先画大图景

从读者要完成的任务出发：输入是什么，最终希望得到什么，朴素方法在哪些条件下失败，哪些机制各自补哪一块。开头用短段落或小图呈现，不提前抛出全部术语。

已有基础视为起点而非重教一遍。主题很大时先圈定一个完整闭环，把不同层次／路线标成分支。

## 每个重要章节的内部蓝图

| 字段 | 要回答的问题 |
| --- | --- |
| Previous | 读者已经理解／前文已经解决了什么？ |
| Gap | 在哪个条件下仍出现什么具体问题？ |
| Bridge | 为什么现在处理这个缺口，需要什么新能力？ |
| Mechanism | 新概念改变哪个量、数据结构、决策或执行环节，为什么有效？ |
| Tradeoff | 引入什么成本、假设、误差或尚未解决的问题？ |
| Next | 本节产物给谁使用，剩余问题由哪一节承接，或为何到此为止？ |

把每格写成一个具体句子即可，不输出私人推理过程。最终正文把这些关系写成自然的开篇与收束，不展示六字段表，也不在每小节复制固定句式。

若 Gap 只能写“还不了解 B”，需要重新找任务上的缺口。若 Next 无真实后继，写“本范围到此结束”，不虚构预告。

## 问题要收回来

给前文重要的未解问题安排落点：问题 → 提出章节 → 回收章节／明确范围外。后文解决时主动点名原问题，并说明它是全部解决、在假设下解决，还是仅缓解。

可用的过渡：“我们已把重复计算变成一次查找，但缓存容量有限。现在缺的不是更快的查找，而是满了以后依据什么留下数据。”这里的转折由真实约束驱动。

需要修改的过渡：“上一节介绍了缓存，本节介绍 LRU。”它只报告目录移动，没有说明依赖。

过渡只需准确、具体；无须每次重复“已经……但是……因此……”的表面句式。

## 跨主题示例

以下是教学组织例子，不构成相关主题的完整事实来源。写具体笔记时按当前来源、假设与读者基础校准。

### 缓存：复用与容量是两个问题

- Previous：相同请求可以复用结果，命中时少做一次昂贵计算。
- Gap：所有结果一直保留会超过容量。
- Bridge：需要一个在容量用尽时选择删除对象的规则。
- Mechanism：若用“近期使用”作为未来复用的线索，就需要维护访问次序并从最久未用端淘汰。
- Tradeoff：访问也要维护元数据；这种线索在循环扫描等访问模式下可能不准。
- Next：用访问序列验证边界；TTL 解决过期有效性，是另一条分支，不是淘汰策略的自然替代。

### 数据库：从定位记录到查询代价

扫描能找出满足条件的记录，但大量不匹配记录也被读取 → 索引用额外结构缩小候选集合 → 仍可能需要回到原记录获取其他列 → 在实际存储模型下讨论覆盖查询及其额外存储／写入维护代价。

讲解时收回“读了多少不必要数据”，不要把各种索引硬排成谁取代谁；不同查询条件可能走不同分支。

### 编译：从局部计算到跨分支可用性

同一基本块里能看见重复表达式 → 控制流分支让某个结果不一定在所有到达路径上可用 → 需要分析哪些定义能到达使用点／哪些事实在各路径成立 → 数据流合并规则决定何时可以安全复用 → 循环引入迭代求解与成本。

这里收回的是“为什么这次替换不会用到尚不存在或已过期的值”，而不只是给分析算法取名字。

### 模型学习：目标量到可计算信号

已定义希望优化的总体目标 → 期望无法精确遍历 → 用有限数据构造估计量 → 分析其偏差、波动与计算成本 → 根据具体缺口引入改进。估计目标、采样来源、梯度路径是三件需要对齐的事；不同方差控制与优化方法可以互补，并非一条必然演化链。

## 进入深度规划的门槛

每个核心章节都有“为什么现在出现”的答案；每条箭头能说清是因果、数据流、前置依赖还是对比。重要问题有回收位置，独立主题没有被强接成假因果。
