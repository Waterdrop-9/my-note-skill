# Technical Depth · 精确到能复述和实现

涉及数学、算法、系统流程或代码时读取。用学习目标决定深度，不按公式数量判断质量。

## 公式什么时候必须出现

当更新方向、条件分支、概率校正、复杂度、约束或关键取舍依赖精确关系时，保留核心公式。概念只涉及结构且公式不能增加理解时，无须装饰性数学。

公式前说明它要解决的具体问题；公式后先读出整体意思，再解释符号和关键项。必要时标注求和范围、采样分布、单位、张量维度、索引范围与适用条件。

同一符号保持同一含义，状态快照用明确下标；一个量重新定义时指出变化。不要把一个公式孤零零放在卡片里让读者猜。

## 区分陈述身份

| 身份 | 正文交代什么 |
| --- | --- |
| Definition / 定义 | 我们约定这个量是什么；它本身不证明有效 |
| Theorem / 定理 | 前提、结论与应用处；证明展开取决于是否影响主线 |
| Exact identity / 恒等关系 | 为什么等式成立，变形用了哪个性质 |
| Estimator / 估计量 | 估计哪个目标、样本来自哪里、样本量及偏差／方差条件 |
| Approximation / 近似 | 省略或替换了什么、什么时候合理、引入什么误差 |
| Surrogate / 替代目标 | 实际优化的表达式如何关联理论目标，以及并非等价的地方 |
| Heuristic / 经验选择 | 为什么这样选、已知局限；不包装成数学必然 |

符号用 `=`、`≈` 和“定义为”准确区分。有限样本平均是一个估计量，不会因为写了求和就等于总体期望。

## 推导保留决定理解的步骤

每次关键变形回答：为什么向这个方向变形？用了什么性质？需要哪些前提？

以下环节通常不能跳：分布变化与支持集、期望与梯度交换、独立性／条件期望、被消去项为何为零、归一化、符号改变与分段选择、梯度停止的原因。只说“显然”不能代替解释。

普通代数移项可合并；难但主线依赖的推导应展开到读者能独立复述。不把长证明自动设为必读，也不把关键证明因为难就放进 OPTIONAL。

## 理论 → 算法 → 实现

先按真实执行顺序写输入 → 操作 → 输出 → 下一步用途，再把公式嵌回执行过程。必要时用一张映射表：

| 符号／代码变量 | 来自哪里 | 形状／单位 | 何时更新或冻结 | 梯度／生命周期 |
| --- | --- | --- | --- | --- |
| 当前主题中的关键量 | 数据、采样、前向或上一阶段输出 | 仅写有助理解者 | 阶段与版本 | 参与优化／固定目标／状态存储等 |

训练场景明确 rollout／数据准备、update、推理各自执行什么，固定的是快照还是当前值。解释 detach 是切断哪条梯度路径、为什么目标中不需要该路径；不要把“避免报错”当作理论理由。

系统场景对应为离线准备／在线查询、读路径／写路径、生产／消费、存活／失效等阶段，不强行套训练术语。不适用项无需出现。

## Shape、单位和代码

当广播、矩阵乘法、转置、mask、求和轴或 batch／时间维度容易混淆时写 shape，并在关键转换处验证维度相容。非张量主题不用强加 shape 表；容量、延迟、字节等单位同样重要。

正文优先最小闭环或伪代码。变量命名尽量对应公式；确实不同则给映射。注释解释为什么这么写以及写错的后果，不逐行翻译语法。

明确标注伪代码、教学简化代码、可运行实现；说明简化掉的条件。可运行代码做与机制相关的检查，例如分支、边界、数据形状、梯度路径或不变量；只有实际运行才报告通过。

展示代码使用 `<pre><code>` 保留缩进并转义 `&`、`<`、`>`。公式布局与渲染见 [Style C 布局](layouts-deep-study.md)，排版不得改变公式语义。

## 分支和例子

条件分支先展开，写选中表达式／执行操作、输出变化及相关边界，再归并成模式。特别区分单个样本的梯度、一个损失项的梯度和所有参数的更新。

例子优先暴露两个容易混淆的对象或条件变化后的不同结果。数值必须可复算；教学数值不标成论文实验。最后用文字收回“这个结果如何回答开头的问题”。
