# Learning ROI 与 Interview Priority

深度规划时读取；最终优先级取决于读者已有基础、目标与预算，而非知识点的名气。

## 三层深度

| 层次 | 选择依据 | 掌握到哪里 |
| --- | --- | --- |
| CORE / 核心必会 | 后续主线依赖、决定机制或能否正确应用 | 说清问题、设计原因、核心机制与代价；适用时复述关键推导／写最小实现 |
| FOLLOW-UP / 追问准备 | 边界、替代方案、易混区别、关键实现取舍 | 回答“去掉会怎样”“为何不用另一种”“何时不成立” |
| OPTIONAL / 选读扩展 | 不影响当前闭环的变体、长证明、历史与工程旁支 | 知道解决什么额外问题、与主线的关系，以及何时值得继续学 |

难但影响主线的内容必须留在 CORE。若 FOLLOW-UP 或 OPTIONAL 被核心解释引用为必要前提，就提升它的优先级或补上主线解释。

## 如何分配深度

为每个重要知识点记录：优先级、读者卡点、所需表达（推导／核心公式／例子／比喻／代码／流程／对比／一句扩展）、具体停止标准。不是每项都需要所有表达。

优先深挖能改变理解和判断的内容；仅需分清适用条件的方案用共同维度对比。没有当前使用情境的高级旁支，说明用途和入口即可。

时间紧时先限定一个完整闭环，再压缩重复与旁支。若用户给出的时间容不下其目标所需 CORE，在交付说明中告知范围，或在用户明确要求导读时给出分段阅读建议；默认不把时间预算和生成计划写进笔记头部。不假装删去关键机制后仍达成同等深度。

内部先确定主线阅读顺序和三级标识；只有它们能帮助读者实际取舍时才在局部显示。章节末可用具体任务说明停止标准，例如“能解释命中为何改变淘汰顺序，并手推一次淘汰”；不要求每节都显示，也不要只写“理解本节”。

## 面试是理解的压缩

先写正文，再为最重要的主题按需生成简短回答：

**结论 → 原因 → 关键代价／边界 → 递进追问及回答要点。**

第一问检查机制，后续追问可以改变条件、去掉一步或比较替代方案。给少量有区分度的问题即可，不按固定题数填充。每个回答能定位到正文解释，必要时用章节链接回跳；新出现的必要知识先补到正文。

HTML 自测与面试问答采用“问题可见、答案默认折叠、点击揭晓”，按 [问答组件规范](components.md#自测问答先作答再揭晓) 渲染；正文中的必要解释保持直接可读。

比较方法使用共同决策维度：解决的问题、关键改动、数据／状态要求、计算／存储成本、适用条件。让读者能解释某条件下为何选择某方法，而不是背各自优缺点。

用户不需要面试时，可以保留掌握标准与简短自测，不强加面试区。没有可靠招聘依据时不用“必考”“高频率”等判断；可说“建议优先掌握”。
