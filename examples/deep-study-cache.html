这里研究一个小而完整的问题：单线程程序反复请求同一个 key 的稳定结果，如何减少重复计算，同时不让缓存无限增长？容量按条目数计算，值在本文范围内不变。先理解这个闭环，再考虑真实系统里的额外约束。

复用计算结果→ 容量要求取舍→ 维护访问次序→ 检验策略边界

01先算清楚：少做哪一步才会快？

假设同一个 key 的结果需要昂贵计算，每次重新算都要付出成本。字典已经能按 key 查值；把算过的结果存起来，下次命中就直接返回，少做一次原计算。没有命中仍然要算，因此缓存并不保证每次访问都更快。

先用一个教学模型回答“什么情况下值得缓存”：每次查询缓存花 \(t_c\)，未命中后额外计算花 \(t_f\)，命中概率为 \(h\)。暂时忽略插入、顺序维护、并发和延迟波动。每次请求都先查缓存，所以命中总耗时是 \(t_c\)，未命中总耗时是 \(t_c+t_f\)。

\(h\)
命中概率，范围为 0 到 1，由访问分布、容量与策略共同决定。
\(t_c, t_f\)
缓存查找耗时与未命中后额外计算耗时，使用相同时间单位。
\(T\)
一次请求的总耗时；\(\mathbb{E}[T]\) 是模型中的期望。

第二行把两条路径都要付出的查找成本 \(t_c\) 提了出来。相比每次直接计算的 \(t_f\)，节省的是 \(h t_f-t_c\)：命中省下的计算必须抵得过每次查询缓存的成本。因此在这个模型中，\(t_f>0\) 时只有 \(h>t_c/t_f\) 才更快。

构造一个小例子：\(t_c=1\) ms、\(t_f=9\) ms、\(h=0.8\)，期望耗时为 \(1+0.2\times9=2.8\) ms，而直接计算需要 9 ms。若 \(h=0\)，反而要 10 ms。这些是教学数值，不是性能实测。

关键洞察 · 缓存快在少做了原计算

不是给计算加上“缓存”这个名字就会更快。收益来自命中时省掉的那段工作，代价是查找、存储和维护；第 04 节还会补回这里暂时忽略的成本。

实际观测 \(N\) 次请求，用“命中次数 / \(N\)”得到的是命中率估计量 \(\widehat h\)。一次序列的统计不是未来访问的保证，访问模式改变后命中率也可能变。

掌握到这里：能指出命中省掉哪一步、未命中多付哪一步，并解释 h = 0 时为何可能更慢。

02容量满了，凭什么删这个？

复用解决了重复计算，容量问题还在

前面把计算结果存进字典，但如果所有结果一直保存，空间会持续增长。现在需要补的能力是：容量用尽时，依据什么决定保留谁？

设容量 \(C=2\)，初始为空，依次访问 A、B、A，再放入 C。按插入顺序，A 比 B 早；但按最后使用时间，B 比 A 久未使用。只允许保留两个条目，我们必须明确采用哪条规则。

同样的容量，不同的选择依据

FIFO

依据最初进入缓存的次序，淘汰最早插入的 A。命中不改变插入次序。

LRU

依据最后一次使用的次序，淘汰最久未使用的 B。因此命中也必须刷新次序。

LRU（Least Recently Used）定义了一个淘汰规则：满时删掉最久未使用的条目。它借用“最近用过的东西可能很快再用”这条线索；这是一种策略假设，不是能预测未来的定理。操作系统中的页面替换也讨论这类基于访问历史的策略。[1]

维护一个从“最久未使用”到“最近使用”的次序。查到 key 不仅返回值，还把它移到最近端；未命中则计算并插入最近端，满时先移除最久端。下面按读取请求展开，避免把“更新次序”误记成“每次都淘汰”。

条件变化后，究竟执行什么？
条件实际操作结果一句人话
命中移到最近端，返回值容量不变，次序刷新用过就重新排队
未命中，未满计算成功后插入最近端增加一项还有位置，直接留下
未命中，已满计算成功后删最久项，再插入保持容量满了才请旧的离开
容量为 0计算并返回，不存储缓存始终为空只计算，不留存
计算失败传播异常，不删、不插入原缓存不变新结果没拿到，先留着旧的

手推一次：第三次访问 A 为什么关键？

C = 2，从空缓存访问 A、B、A、C、B；左旧右新
请求命中？移除请求结束后的次序
A否无[A]
B否无[A, B]
A是无[B, A]
C否B[A, C]
B否A[C, B]

五次访问只有一次命中。第三次 A 把次序从 A、B 改成 B、A，导致随后删除 B。如果只返回值却不换序，就会在后面误删刚访问过的 A。

归并起来只有两个主要模式：命中更新次序，未命中按容量决定是否淘汰。一句话记忆：“用过就排到最近端，满了才请最久没用的离开。”队伍位置只映射访问次序，不代表条目的价值。

掌握到这里：能独立手推上述序列，并说明第三步如何决定第四步删除谁。

03次序怎么变成代码里的状态？

“满时删谁”的问题已经有答案，但如果每次命中都扫描列表找位置，维护次序本身就会变贵。我们既需要按 key 快速定位，也需要把任意位置的条目快速移到最近端。

常见结构是哈希表保存 key → 节点的索引，双向链表保存访问次序。命中后通过节点的前后指针把它摘下，再接到尾部，不需要从头找前驱。最久项就在头部。数组在中间移动条目则可能需要搬动多项。

在哈希表平均常数查找的假设下，查找、移位与淘汰的缓存管理平均为 \(O(1)\)，状态占用 \(O(C)\) 个条目及其元数据。哈希退化或昂贵的 key 操作会改变这个估计；未命中时计算结果的成本不在这个 \(O(1)\) 内。

下面用 Python 标准库 OrderedDict 表达同样的顺序操作，省去链表样板。move_to_end(key) 把条目移到末尾，popitem(last=False) 删除首项；这些 API 语义可查官方文档。[2]

一次请求的执行顺序

  1. 输入 key。查 items；命中则移到末尾并返回保存的值。
  2. 未命中时调用 load。由 load(key) 产生 value。失败时还没修改缓存，因此原状态保留。
  3. 维护容量与次序。零容量直接返回；否则满时删首项，再把新条目放到末尾。
  4. 返回结果。items 留给下一次请求使用，它是跨请求保留的状态。

capacity 对应前文 \(C\)，items 始终左旧右新。下方是教学简化的可运行实现：key 必须可哈希，load(key) 在本例中提供稳定结果；未实现并发、过期时间或按字节计费。

from collections import OrderedDict


class LRUCache:
    def __init__(self, capacity: int):
        if type(capacity) is not int or capacity < 0:
            raise ValueError("capacity must be a nonnegative integer")
        self.capacity = capacity
        self.items = OrderedDict()

    def get(self, key, load):
        if key in self.items:
            # 命中也刷新次序，否则会误删刚访问过的条目。
            self.items.move_to_end(key)
            return self.items[key]

        # 先拿到新结果再淘汰，load 失败时保留现有缓存。
        value = load(key)
        if self.capacity == 0:
            return value
        if len(self.items) == self.capacity:
            self.items.popitem(last=False)
        self.items[key] = value
        return value

容量和次序的不变量

每次请求结束，条目数不超过 capacity；正容量且请求成功时，最后访问的条目位于末尾。用 key in items 判断命中，因此缓存值为 None 也不会被误当作未命中。

掌握到这里：能把条件表的每一行对应到代码，说明为什么先 load、再淘汰，以及命中为什么不调用 load。

04最近用过，为什么仍会猜错？

FOLLOW-UP 我们已经能维护容量，但“可以实现”并不等于“所有访问模式下都更快”。现在收回第 01 节暂时忽略的成本，并检验第 02 节使用的线索。

代价不仅是保存值：顺序结构还占内存，每次命中也要更新元数据。\(C\) 表示条目数，不保证总字节数固定。真实系统还可能有锁与协调开销，这些都不在开头的简化延迟模型中。

一个足以推翻“一定快”的反例

仍取 \(C=2\)，循环访问 A B C A B C。第一轮结束保存 B、C；再要 A 时删 B，接着要 B 时删 C，再要 C 时删 A。缓存一直在追赶，这个序列从空状态开始每次都未命中。

容易误解 · LRU 并不保证高命中率

LRU 用近期访问猜后续复用。循环扫描可以让这条线索失效，因此前文的 \(h\) 可能降到零；第 01 节已经说明，零命中时缓存查询反而是额外成本。

另一个边界是有效性：LRU 解决容量满时先删谁，TTL 按时间限制缓存值的有效期，两者可以并用。即使时间未到，源数据也可能已经更新；是否返回最新数据还需要相应的失效机制。本文假定值稳定，所以到这里指出缺口，不继续展开分布式协议。

掌握到这里：能用访问序列说明策略假设如何失效，并分清“空间装不下”与“内容过期了”两个问题。

05将理解压缩成口述

主线回收

复用减少昂贵计算；容量迫使我们选择保留谁；LRU 用最近访问决定次序，因此命中也要维护状态；这种维护有成本，而近期访问未必预测未来。每一块都对应前面留下的一个问题。

口述回答 · 结论、原因、边界

LRU 在有限容量下淘汰最久未使用的条目，用近期访问作为复用线索，所以命中也必须调整次序。哈希索引加双向链表可在通常的哈希假设下做到平均常数时间的管理，但会增加存储和更新开销，循环扫描也可能让它一直不命中。

命中不调整会怎样？用 A、B、A、C 说明：第三次 A 没刷新，随后会误删 A，次序更接近插入顺序。

O(1) 包含 load 吗？不包含，它描述的是缓存管理；原计算有自己的成本。

LRU 能保证最新数据吗？不能；淘汰次序没有判断源数据是否变化，见有效性边界。

OPTIONAL 在真实缺口出现时再扩展

当并发请求、值会变化或条目大小悬殊成为实际需求，再学并发控制、失效策略和按字节容量。现在知道它们分别补哪种缺口即可，无需先背一套完整缓存架构。
